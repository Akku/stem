# Tron mode: before and after a run

Rules: `R-TRON` in `docs/agent/TRON.md` (session duties, role tiers), `R-BATCHING` (approval of a batch), `R-DESIGN` (alignment). Do not repeat them here. The runner is `scripts/tron.py`; this skill starts a run only after the user's go (section 2).

## 1. Prepare the milestone: one setup message
Send the setup items in ONE numbered message (`R-BATCHING`), each with the default you propose, so the user answers compactly (e.g. "ok", or "2b, 7: sonnet"); ask nothing per item. Apply the answers, then commit so the tree is clean.
1. Milestone and tasks: the ready tasks in order; every task has acceptance criteria and a `size-*` label (name the ones that lack them and your fix).
2. Decision frame (`docs/agent/DECISION_FRAME.md`): the lines you would change for this milestone, or "as is".
3. Invariants (`docs/agent/INVARIANTS.md`): the project-specific lines you would add.
4. Acceptance scenario: `docs/agent/tron/ACCEPTANCE-<milestone>.md` (or `tron.acceptance_scenario`): what the user would click or run to judge the result; draft it (after the sweep, from its draft scenario).
5. Limits and evaluator: default `max_cost`, `max_hours`, `max_tasks`, evaluator mode (`off|milestone|task`), `pause_after`; the user approves the budget with the go (section 2), not here.
6. Start-and-smoke command: `smoke_cmd` or `preview_cmd`/`preview_url` for the product.
7. Commands: the configured command of every role (`worker_cmd`, `evaluator_cmd`, ...; a missing one falls back to `worker_cmd`) and `verify_cmd`. Recommended permission setup: run inside the STEM sandbox (`scripts/sandbox.sh`) with `--permission-mode bypassPermissions` in the role commands, so no permission prompt can stop the run. Never propose a narrow `--allowedTools` list or `dontAsk` for a run; when the config has one, propose switching to the sandbox setup (the check warns).
8. Models: one per role from the `R-TRON` tier table (names live in the config); warn if `CLAUDE_CODE_EFFORT_LEVEL` is set (it beats `--effort`).
9. Permission allowlist for starting the run (security setting, explicit item, never applied by default): if `.claude/settings.local.json` (or `.claude/settings.json`) lacks `Bash(scripts/tron.py:*)` and `Bash(python3 scripts/tron.py:*)` under `permissions.allow`, propose adding them to `.claude/settings.local.json`; add them only when the user says yes to this item, so starting the run triggers no permission prompt.
Edit `docs/agent/stem-config.json` only with the user's answer to this message.

Question sweep (its own step, after the setup message): run `python3 scripts/tron.py sweep --milestone <id>` (a fresh planner session; cost shown), read `docs/agent/tron/SWEEP-<id>.md`. First show every line of `## Pre-decided assumptions` (A<n>) in ONE message as a numbered list and ask only for vetoes by number (e.g. "veto A2"; no answer needed for the rest): move each vetoed line into `## Questions` as the next `- [ ] Q<n>` with the planner's option as recommendation and delete it from the list; the others stay and the runner hands each worker its task's lines as assumptions with basis; those that change the task list (dependency, split, skip) apply now with the `backlog` CLI. Then ask its questions one per message with the planner's recommendation, and record each answer in the file (tick `[x]`, add `Answer: ...`). Answers that change a task or an AC go through the `backlog` CLI now, before the run, so the AC freeze covers them; for the `## Needs the user` lines (N<n>) ask nothing: run `python3 scripts/tron.py split-out --milestone <id>` (it moves each such AC into a new task outside the milestone labelled `waiting` and `tron-user`, the rest stays, ticks N<n> with `Resolved:` and commits) and show its output to the user as ONE info list, no question (a task whose every AC needs the user stays; ask about that one); use the draft acceptance scenario as the base of the acceptance scenario (item 4). Commit the file. The check fails while the sweep is missing, has open questions or an open task still carries an unresolved N line (`tron.sweep: false` opts out).

Environment check (its own step, after the sweep, before the check; TASK-395): the run must not meet an environment gap. For every line of `## Environment needs` (E<n>) of the sweep, run its `Check:` command in the environment the run uses (the sandbox: `docker exec` into it, or its shell; never only on the host) and add the result under the line (`Checked: present` or what you did). Where a need is missing, fix it yourself when that is install or configuration inside the run environment (a package, a service start, a copied file) and check again; then tick `[x]`. When the fix needs the user (a secret, a paid service, real data, a large install) or the AC cannot get E2 evidence there, show the gaps in ONE message with options and a recommendation: a) the user provides it, b) split or skip the task (`backlog` CLI; skip via a `Skip:` line), c) accept that the task blocks; apply the answer, tick `[x]` with `Checked: <decision>`. Also compare the git-ignored files the tests read between host and sandbox. Commit the file. The check fails while an E line of an open task is unticked or has no `Checked:` line.

## 2. Check and start
- Run `python3 scripts/tron.py check --milestone <id>` and fix what it lists (it exits 1 with a list; warnings do not block). It includes the preflight (`docs/agent/TRON.md` 'Preflight and keep-awake'; one cheap agent call, `--no-smoke` skips it). For a long run ask once whether the machine should stay awake (recommended for runs over an hour); on yes set `tron.keep_awake: true`, and in the sandbox tell the user to start it on the Mac with `scripts/sandbox.sh start <name> --keep-awake`.
- When it prints `READY` (ideally after `--dry-run`), ask ONE question that is both budget and go: show the exact `start:` line, the limits (`max_cost`, `max_hours`, `max_tasks`) and the expected cost together (a run costs money). A yes approves the budget and starts the run, with no second confirmation; changed numbers in the answer go into the config first (commit), then start.
- After the yes, start the run yourself with `--detach` (the `start:` line) as a background command that notifies you when it exits (Claude Code: Bash with `run_in_background`); `--detach` makes the run its own process, so it goes on when this session ends. Never ask the user to start it, open a terminal or type a command. Say once where the report will appear and that you read it yourself when the run ends.
- While the run holds `docs/agent/tron/LOCK`, commit nothing on `tron/<milestone>` (the pre-commit hook refuses it); repairs wait until the run has stopped (`docs/agent/tron/STOP` stops it after the current session). A resume moves the interrupted task's base past such repair commits.
- During the run ask nothing and wait for no input: no questions, no "tell me when it is done". When the process exits, read `docs/agent/tron/REPORT-<run>.md` yourself and continue with section 3.

## 3. After the run
- Read `docs/agent/tron/REPORT-<run>.md` yourself, then give the user: Done, Blocked, evaluator findings (risks without a 'Must come back' frame line are listed there only), cost, branch `tron/<milestone>`. The user decides on merging; the run never pushed, tagged or merged.
- Ask the report's `## Questions for you` block in ONE message, numbered as in the report with its options and recommendations; the user answers compactly (e.g. `1a, 3b`). Ask nothing per item. Apply each answer without asking again:
  - a draft question (Blocked, Doctor, split, risk): record the answer in the draft, change the task with the `backlog` CLI where it says so (a risk: accept, or create a task); then offer to run again (it resumes);
  - an assumption without a basis: keep or correct it, and add a line to `docs/agent/PRECEDENTS.md` (`P-<n> | date | kind | ruling | source report <run>`; keep it at 60 lines or fewer);
  - the defects question: `python3 scripts/tron.py defect --run <run> --task TASK-n --text "<what is wrong>"` per defect, or `defect --run <run> --none`; defects go into the tasks as evidence, never fixed silently. When a defect was a miss (the evaluator had passed it), run `python3 scripts/tron.py calibrate --run <run>` (one analyst session; cost shown); its drafted examples come back as the next numbered block of the report, asked in one message again;
  - an example verdict: `calibrate --accept D<n>` or `--reject D<n>`, then commit the evaluator file (the CALIBRATION file is runner output like the journal). Never apply without the user's yes (tier 3, `R-TRON`).
- Commit PRECEDENTS and task changes.
